# SIT Automation Framework - Step By Step Guide

## 1. Purpose

This project is a Python based System Integration Testing automation framework for banking and payment APIs.

The framework is designed to keep test logic configurable:

- Excel files decide which testcases run.
- YAML files define services, API endpoints, authentication, retries, and shared test data.
- JSON files define request payload templates.
- Python modules execute APIs, validate responses, and generate reports.

The main command to run the framework is:

```powershell
python runner.py
```

## 2. Project Structure

| Path | Purpose |
| --- | --- |
| `runner.py` | Main entry point. Loads config, reads Excel testcases, executes APIs, validates responses, and writes reports. |
| `requirements.txt` | Python dependencies required by the framework. |
| `config/servers.yaml` | Service base URLs, enabled or disabled services, and legacy bank URL mapping. |
| `config/apis.yaml` | API definitions, auth settings, token routing, retry settings, and flow definitions. |
| `config/test_data.yaml` | Shared test data tokens used inside JSON request templates. |
| `config/reporting.yaml` | HTML report display and redaction settings. |
| `requests/` | JSON request templates grouped by service. |
| `testcases/` | Excel testcase workbooks. |
| `utils/` | Helper modules for API calls, data generation, template rendering, logging, and service config. |
| `validators/` | Response validation logic. |
| `scripts/` | Helper scripts for creating or inspecting Excel testcase files. |
| `logs/` | Runtime logs generated by execution. |
| `results/` | JSON and CSV result files generated by execution. |
| `reports/` | HTML reports generated by execution. |
| `offline_packages/` | Offline wheel packages for dependency installation when internet access is unavailable. |

## 3. Main Functionality

The framework supports:

1. Multiple service testing.
2. Service specific API configuration.
3. Service enable and disable control.
4. Excel driven testcase execution.
5. JSON request template rendering.
6. Runtime token generation.
7. Authentication token capture.
8. API specific bearer token routing.
9. Parallel execution for independent testcases.
10. Sequential execution for dependent testcases.
11. Polling flows.
12. Chained dependent flows.
13. Response validation.
14. JSON, CSV, HTML report generation.
15. Rotating request, response, validation, framework, and error logs.
16. Offline dependency installation support.

## 7. Service Configuration

Services are configured in:

```text

```

| --- | --- |
| `cas` | CAS service test execution. |
| `acquiring` | Acquiring service test execution. |

Each service has:

```yaml
services:
  cas:
    enabled: true
    display_name: "CAS Service"
    base_url: http://host:port
```

Field meaning:

| Field | Meaning |
| --- | --- |
| `enabled` | Controls whether the service runs by default. |
| `display_name` | Name shown in logs and reports. |
| `base_url` | Base URL used when building API request URLs. |

## 8. API Configuration

APIs are configured in:

```text
config/apis.yaml
```

The file contains:

- Global HTTP defaults.
- Service scoped API definitions.
- Authentication API settings.
- Token routing.
- Flow definitions.
- Legacy fallback API definitions.

Example API:

```yaml
services:
  cas:
    apis:
      payment:
        endpoint: /api/v1/paysyslabs/payment
        method: POST
        headers:
          Content-Type: application/json
```

Field meaning:

| Field | Meaning |
| --- | --- |
| `endpoint` | API path appended to the service `base_url`. |
| `method` | HTTP method, for example `GET` or `POST`. |
| `headers` | Default headers sent with the request. |

## 9. HTTP Retry Settings

Retry settings are configured in:

```yaml
defaults:
  timeout_seconds: 30
  retries: 2
  retry_backoff_factor: 0.5
  retry_status_codes:
    - 408
    - 429
    - 500
    - 502
    - 503
    - 504
```

These settings are used by `utils/api_client.py`.

The API client:

1. Creates a reusable `requests.Session`.
2. Mounts retry enabled HTTP adapters.
3. Logs outgoing requests.
4. Logs incoming responses.
5. Converts JSON responses into Python objects.
6. Returns a normalized response dictionary.

## 10. Authentication And Token Routing

Authentication is defined per service in `config/apis.yaml`.

Example:

```yaml
services:
  cas:
    auth:
      apis:
        - authenticate
      token_json_path: token
```

Field meaning:

| Field | Meaning |
| --- | --- |
| `auth.apis` | API names that must run as authentication testcases. |
| `auth.token_json_path` | JSON path where the token is read from the auth response. |

Token routing decides which token is used by which API:

```yaml
token_routing:
  payment: ib
  directposting: test
```

The runner stores tokens per service and channel. When a later API runs, the runner adds:

```text
Authorization: Bearer <token>
```

if a matching token exists.

## 14. Request Templates

Request templates are JSON files under:

```text
requests/<service>/
```

Examples:

```text
requests/cas/tc001.json
requests/merchant_cas/tc020.json
requests/acquiring/tc001.json
```

The Excel `Request_File` value should match the JSON filename.

Example template:

```json
{
  "rrn": "${RRN}",
  "stan": "${STAN}",
  "senderIban": "${SENDER_IBAN}",
  "receiverIban": "${RECEIVER_IBAN}"
}
```

At runtime, `utils/template_engine.py` replaces placeholders with generated or configured values.

## 15. Runtime Tokens

Generated tokens:

| Token | Meaning |
| --- | --- |
| `${RRN}` | Unique 12 digit reference number persisted in `results/rrn_registry.json`. |
| `${DUPLICATE_RRN}` | Reuses the last generated RRN for duplicate RRN negative cases. |
| `${STAN}` | Random 6 digit trace number. |
| `${DATE}` | Current date as `YYYY-MM-DD`. |
| `${TIME}` | Current time as `HHMMSS`. |
| `${DATETIME}` | Current date and time as `YYYYMMDDHHMMSS`. |
| `${RTP_ID_UNIQUE}` | Unique RTP ID generated at runtime. |
| `${TRANSACTION_ID}` | Usually supplied by a flow or polling step. |

Configured tokens come from:

```text
config/test_data.yaml
```

Keys are converted to uppercase. For example:

```yaml
sender_iban: "PK..."
```

can be used in JSON as:

```text
${SENDER_IBAN}
```

Token priority:

1. Generated defaults.
2. Values from `config/test_data.yaml`.
3. Flow runtime override values.

## 16. Validation Types

Validation is implemented in:

```text
validators/response_validator.py
```

Supported validation types:

| Validation type | Meaning |
| --- | --- |
| `status_code` | Compares HTTP status code with `Expected_Result`. |
| `json_field` | Compares a JSON field value with `Expected_Result`. |
| `response` | Checks whether expected text exists in response text or body. |

### 16.1 Status Code Validation

Excel example:

| Column | Value |
| --- | --- |
| `Validation_Type` | `status_code` |
| `Expected_Result` | `200` |

### 16.2 JSON Field Validation

Excel example:

| Column | Value |
| --- | --- |
| `Validation_Type` | `json_field` |
| `Expected_Result` | `00` |
| `Validation_Rules` | `{"field":"response.response_code"}` |

Backward compatible format:

```text
response.response_code:00
```

### 16.3 Response Contains Validation

Excel example:

| Column | Value |
| --- | --- |
| `Validation_Type` | `response` |
| `Expected_Result` | `success` |

If `Expected_Result` contains comma separated values, all values must be present.

## 17. Execution Order

For each enabled service, `runner.py` executes in this order:

1. Load testcase rows marked `Y`.
2. Run authentication testcases first.
3. Run independent non-auth testcases in parallel.
4. Run sequential non-auth testcases in numeric order.
5. Validate every response.
6. Write reports and logs.

Sequential testcase logic:

- Numeric testcase IDs below 11 are treated as independent.
- Numeric testcase IDs 11 or higher are treated as sequential.

Parallel execution is controlled by:

```powershell
$env:MAX_WORKERS="4"
```

## 21. Flow Support

Flows are defined under each service in:

```text
config/apis.yaml
```

The runner supports two main flow types.

### 21.1 Polling Flow

Polling flow steps:

1. Send initial request.
2. Extract correlation value from initial response.
3. Insert correlation value into polling request.
4. Poll until stop condition is met or timeout occurs.
5. Validate final response.

Config example:

```yaml
flows:
  pacs008_to_pacs002:
    initial_api: pacs008
    initial_request_file: tc004_pacs008.json
    polling:
      api: pacs002status
      request_file: tc005_pacs002_poll.json
      interval_seconds: 5
      timeout_seconds: 60
      correlation_from_response_json_path: transaction_id
      correlation_in_request_json_path: transaction_id
      stop_when:
        type: json_field
        field: transaction_status
        allowed_values:
          - ACSP
          - RJCT
```

### 21.2 Chained Dependent Flow

Chained flow steps:

1. Send initial API request.
2. Check if initial response has success code.
3. Map response fields into template tokens.
4. Render the next request template.
5. Send next API request.
6. Validate final response.

Config example:

```yaml
flows:
  Chained-Dependent:
    initial_api: getdefaultaccount
    on_success:
      next_api: directposting
      next_request_file: tc174_payment_from_alias.json
      mappings:
        - from: default-account-byalias.id.iban
          to: RECEIVER_IBAN
```

Excel usage:

| Column | Value |
| --- | --- |
| `Flow_Config` | Flow name from `config/apis.yaml` |
| `API_Name` | Initial API or flow API according to local convention |
| `Request_File` | Initial request template unless overridden by flow config |

## 24. Adding A New API Testcase

Follow this standard sequence.

### Step 1: Add API Definition

Edit:

```text
config/apis.yaml
```

Add the API under the correct service:

```yaml
services:
  cas:
    apis:
      new_api:
        endpoint: /api/v1/example
        method: POST
        headers:
          Content-Type: application/json
```

### Step 2: Add Token Routing If Needed

If the API needs a bearer token, add token routing:

```yaml
token_routing:
  new_api: default
```

### Step 3: Create Request Template

Create:

```text
requests/<service>/<request_file>.json
```

Example:

```text
requests/cas/tc360.json
```

### Step 4: Add Excel Row

Open the correct workbook:

```text
testcases/sit_testcases.xlsx
```

Add a row with:

- `TC_ID`
- `Description`
- `Bank`
- `API_Name`
- `Request_File`
- `Expected_Result`
- `Validation_Type`
- `Execute (Y/N)`

### Step 5: Run Only The Target Service

```powershell
$env:ENABLED_SERVICES="cas"
python runner.py
```

### Step 6: Review Output

Check:

```text
reports/
results/
logs/error.log
logs/validation.log
```

## 27. Troubleshooting

### 27.1 Request File Not Found

Check:

- Excel `Request_File` value.
- File exists under `requests/<service>/`.
- Service resolution selected the expected service.

### 27.2 API Definition Not Found

Check:

- Excel `API_Name`.
- API exists under correct service in `config/apis.yaml`.
- Service is enabled in `config/servers.yaml`.

### 27.3 Unauthorized Response

Check:

- Auth testcase exists and is marked `Y`.
- Auth API is listed under `auth.apis`.
- `auth.token_json_path` matches the actual auth response.
- API has correct `token_routing`.

### 27.4 Validation Fails

Check:

- `Validation_Type`.
- `Expected_Result`.
- `Validation_Rules`.
- Actual response in the HTML report.
- `logs/validation.log`.

### 27.5 Service Does Not Run

Check:

- `enabled` value in `config/servers.yaml`.
- `ENABLED_SERVICES` environment variable.
- `DISABLED_SERVICES` environment variable.
- Workbook rows marked `Y`.

## 28. Security And Data Handling

This project may contain internal URLs, account identifiers, request payloads, test data, logs, and reports.

Standard practices:

1. Do not commit real production secrets.
2. Do not share generated reports externally without review.
3. Avoid committing `.pyc` files.
4. Avoid committing `__pycache__` folders.
5. Avoid committing generated logs unless they are specifically required.
6. Avoid committing generated reports and results unless requested.
7. Rotate any credential that was pasted into chat, logs, or documentation.

Recommended files to commit:

- Source code.
- Config changes that are intended for the team.
- Request templates.
- Testcase workbooks.
- Documentation.

Files usually not recommended for normal commits:

- `logs/`
- `reports/`
- `results/`
- `__pycache__/`
- `*.pyc`
- local zip backups.
